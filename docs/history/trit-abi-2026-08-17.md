# `[trit]` has two incompatible runtime representations

Measured 17 August 2026, immediately before a hard reboot. Written against the
uncommitted maniTC working tree (the `LEN_PREFIXED` guard in
`src/semantic/analyzer/expressions.rs`), which is unchanged and unpushed.

© Manish Jagdish Thatte

---

## What the guard was covering up

The guard refuses `[trit]` as the first argument to `pack_trits`,
`trits_to_str` and `from_balanced_ternary`. Its comment says an unsized `[trit]`
"passes the bare pointer through, and the callee then reads its first element as
the length". That is true of *some* `[trit]` values and false of others, and the
difference is the actual bug.

`src/codegen_llvm/helpers.rs` states the convention plainly:

> a `[trit]` value is a length-prefixed i64-slot array:
> mem[0] = len, mem[1..=len] = trits, least-significant trit first

But that convention is honoured by only one of the two ways a `[trit]` can arise.

| How the `[trit]` was produced | Actual representation | Length prefix? |
|---|---|---|
| Native producer (`math::to_balanced_ternary`) | i64 slots, `mem[0] = len` | **yes** |
| Sized `[trit; N]` passed to a `[trit]` parameter | raw i8 slots + hidden trailing length arg | **no** |

`ternary_pack_trits` / `ternary_trits_to_str` both begin
`%len = load i64, ptr %arr` — they assume the first form. Handed the second they
read a trit as a length.

## Measured, with the guard disabled

`to_balanced_ternary(14)` is `-1,-1,-1,+1` LST-first, i.e. `---+`.

| Case | LLVM | T3 | Correct? |
|---|---|---|---|
| A `let a: [trit] = math::to_balanced_ternary(14)` → `trits_to_str(a)` | `---+` | `---+` | ✅ |
| B `let b: [trit] = [+, 0, -]` → `trits_to_str(b)` | `+0-` | `+0-` | ✅ |
| C `let c: [trit; 3] = [+, 0, -]` → `trits_to_str(c)` | `+0-` | `+0-` | ✅ |
| **D** sized array passed through a `fn show(t: [trit])` param | **no output (crash)** | **`0`** | ❌ |
| E producer result passed through the same param | `---+` | `---+` | ✅ |

**A, B and C all work with the guard removed.** The guard is therefore refusing
three compositions that are correct — including the documented stdlib pairing
`to_balanced_ternary` → `trits_to_str` that `examples/ternary_demo.mt` uses, which
is why that example stops compiling.

**D is the genuine defect**, and the guard does not catch it: `show`'s parameter
is spelled `[trit]`, so the call inside `show` is `trits_to_str(t)` where `t` is
already a `[trit]` — the guard sees nothing wrong at that call site, because the
raw-vs-prefixed distinction is invisible in the type. The same function body is
correct or crashing depending on what its *caller* passed.

## Why the marshalling is where it is

`src/ir/lower/lower_expr.rs` (~line 480, `LP_FUNCS`) builds the length-prefixed
buffer only for `ManiType::Array(Trit, Some(n))` — it allocas `[i64 x n+1]`,
stores `n`, and widens each i8 trit into an i64 slot. That is exactly right for a
raw sized array and exactly wrong to skip for a raw *unsized* one.

## The fix, and why it cannot be done at the call site alone

The information needed — "is this pointer already length-prefixed?" — is not
recoverable from `ManiType::Array(Trit, None)`. Two options:

1. **Make the representation uniform.** Have unsized `[trit]` always be the
   length-prefixed i64 form, and marshal at the point a sized array is *coerced*
   to an unsized parameter, not at the ternary call. This deletes the guard and
   fixes D. It touches `lower_expr` argument coercion and both backends' calling
   conventions.
2. **Carry the length instead of prefixing.** Drop the prefix convention and pass
   `(ptr, len)` to these three helpers, using the hidden trailing length the
   compiler already computes (`append_unsized_len_args` /
   `unsized_array_len`, `src/ir/lower/mod.rs:83–128`). Changes the three helper
   bodies in `helpers.rs`, T3 syscalls 8/11/12, and the emulator.

Option 2 fits what the compiler already does everywhere else for `[T]` and
removes a bespoke convention. Its risk is `unsized_array_len`'s fallback of `0`
when no length is recoverable — that must become a hard error, or D turns from a
crash into a silent empty result, which is worse.
